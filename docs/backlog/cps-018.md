# [CPS-018] A release publishes the update to the Microsoft Store

**Status**: In Progress
**Priority**: High
**Component**: `.github/workflows/release.yml`, `README.md`; outside the repository: Partner Center, Microsoft Entra ID, the repository's secrets
**Related**: [CPS-010](cps-010.md) (first Store release, by hand; release-please and the bundle job)

**Summary**:
As the author, I want merging release-please's release pull request to publish the update to the Microsoft Store as well, so that a release needs no upload by hand in Partner Center.

**Description**:
CPS-010 releases by hand: the release job attaches the `.msixbundle` to the GitHub release, and the
author uploads it in Partner Center. Microsoft's Store Developer CLI (`msstore`) publishes updates
of an MSIX app from CI ("You must complete your app's first publication to the Microsoft Store
through Partner Center. After your app is published, you can use the Microsoft Store Developer
CLI to publish subsequent updates", Microsoft Learn, Microsoft Store Developer CLI (MSIX),
2026-10-01). It runs on Windows, macOS and Linux and supports free apps only, which Shortcuts is.

The release job's bundle step is followed by a Store step on `windows-latest`:
`microsoft/microsoft-store-apppublisher` (v1.4, 2026-07-21) installs the CLI,
`msstore reconfigure --tenantId … --sellerId … --clientId … --clientSecret …` configures it
without a prompt, and `msstore publish <bundle> --appId 9NN0F5R302LZ` uploads the bundle and
commits the submission to certification; `--noCommit` keeps it as a draft. The credentials come
from repository secrets.

Microsoft Learn names only `.msix` and `.msixupload` as input of `msstore publish`, but a
`.msixbundle` works: Microsoft's own WinUI Gallery submits one with
`msstore publish . -i <bundle>.msixbundle -id <product> …` (docs/PublishingNewVersion.md), and
ggml-org/Llama-Windows submits its `.msixbundle` from its release workflow with the same CLI.

Prior art: 8LWXpg/CmdPal-ProcessKiller, where `scripts/publish-store-bundle.ps1` comes from,
has no CI; it builds and uploads by hand. ggml-org/Llama-Windows (`.github/workflows/release.yml`,
job `store`, docs/store-publishing.md) is the model for this item: it checks that every secret
is set before `reconfigure`, finds exactly one bundle, and adds `--noCommit` while the repository
variable `STORE_NO_COMMIT` is not `false`, so the first runs end as drafts.

The author's steps, as they need the author's accounts:
- associate a Microsoft Entra ID tenant with the Partner Center account (Partner Center can
  create one for free);
- register an Entra application, give it the Manager role in Partner Center, and create a
  client secret (at most 24 months; Microsoft recommends less than 12);
- look up the seller ID in Partner Center (Account settings → Identifiers);
- store tenant ID, seller ID, client ID and client secret as repository secrets.

Raised on 2026-11-18.

**Acceptance Criteria**:
- [ ] Merging a release pull request uploads the release's bundle to the Microsoft Store and submits it, without a step in Partner Center
- [ ] The credentials are repository secrets; nothing secret is in the repository
- [ ] The README says how to renew the client secret before it expires, and what fails if it has expired

**Scope Decisions**:
- 2026-11-24: The repository variable `STORE_NO_COMMIT` switches between draft and submission. While it is not `false`, `msstore publish` runs with `--noCommit` and the submission stays a draft; the first run ends that way, and the author checks the draft in Partner Center, submits it there and sets the variable to `false`. From then on a merge submits without a step in Partner Center (AC 1); setting the variable back to `true` returns to drafts without a code change. Reason: the Store step runs only on a release, so no pull request can try it beforehand. No GitHub environment with required reviewers: it would bring back the manual step AC 1 removes.

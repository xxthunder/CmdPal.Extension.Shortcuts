# [CPS-019] A release puts the Store-signed bundle on GitHub and in WinGet

**Status**: In Progress
**Priority**: Medium
**Component**: `.github/workflows/release.yml`, `scripts/publish-store-bundle.ps1`, `THIRD-PARTY-NOTICES.md`, `store/gallery/extension.json`, `README.md`, a scoop manifest; outside the repository: `microsoft/winget-pkgs`, `microsoft/CmdPal-Extensions`
**Related**: [CPS-010](cps-010.md) (first Store release and the Gallery entry), [CPS-018](cps-018.md) (a release publishes the update to the Store), shortcuts [SC-089](https://github.com/xxthunder/shortcuts/blob/develop/docs/backlog/sc-089.md) (the shortcuts install takes the extension through scoop)

**Summary**:
As a Command Palette user on a machine without the Microsoft Store, I want to install Shortcuts through WinGet or scoop, so that I get the same signed package as Store users.

**Description**:
CPS-010 offers the extension only through the Microsoft Store. Managed work machines often remove
the Store by policy and turn off the winget command line, while they still allow packages signed
by a trusted certificate (`AllowAllTrustedApps` = 1). On such a machine the Gallery's Store button
fails.

The Gallery's WinGet button works there. Command Palette installs through the WinGet COM API, and
the policy `EnableWindowsPackageManagerCommandLineInterfaces` blocks only `winget.exe` and the
WinGet PowerShell module. The author saw this on 2026-11-19 with the extension ProcessKiller: its
WinGet manifest points to a Store-signed `.Msixbundle` on its GitHub release, and the Gallery
installed it on a machine without the Store; `Get-AppxPackage` reports `SignatureKind` `Store`.

The Store re-signs the package with a Microsoft certificate that every Windows trusts. That
signature stays valid outside the Store, so the Store-signed bundle can go to GitHub, WinGet and
scoop with no certificate of the project's own, and with the Store's package identity
`karnomag.ShortcutsforCommandPalette_nsydvkza7yaey` everywhere.

Certification takes time after the submission, so the release workflow cannot wait for the
signed bundle. The work is split in two:

- **The release workflow** (CPS-018) builds the bundle, creates the GitHub release and submits
  the bundle to the Store. Then it ends.
- **`scripts/publish-store-bundle.ps1`**, run by hand by the author once the Store has
  certified the version, is a copy of ProcessKiller's `scripts/publish-msstore-msix.ps1` with
  one step added:
  1. It reads the latest GitHub release and its version.
  2. It asks the Store's delivery service through `store.rg-adguard.net` for the bundle of
     Store ID `9NN0F5R302LZ` and downloads it.
  3. It checks the bundle: the signature is valid and issued by `Microsoft Marketplace CA`, and
     the bundle's identity has the name `karnomag.ShortcutsforCommandPalette` and the release's
     version. A wrong, unsigned or older file stops the script before anything is published.
     This step is the one ProcessKiller does not have.
  4. It uploads the bundle to the release as
     `karnomag.ShortcutsforCommandPalette_<version>.msixbundle` with `gh release upload`.
  5. It runs `komac update`, which opens the pull request that updates the manifest in
     `microsoft/winget-pkgs`.

The scoop manifest that SC-089 installs needs no step of its own: its `checkver` and
`autoupdate` read the GitHub release.

Tried on 2026-11-20 on the author's work machine, for the live v1.0.0: the delivery service
answers through the local proxy, and the bundle it gives is signed by
`CN=Microsoft Marketplace CA G 024` for the publisher `CN=EB467DD7-FED1-4C41-A876-46255255EB4A`,
status `Valid`. The bundle on the GitHub release v1.0.0 is `NotSigned`. Two traps showed up:
Windows PowerShell 5.1 leaves `&amp;` in the link's `href`, which the download server answers
with 403; and its `Get-AuthenticodeSignature` failed to load from a WSL path. The script
therefore needs PowerShell 7 and decodes the link.

Once, after the first WinGet manifest is merged: `store/gallery/extension.json` gets a `winget`
install source next to `msstore`, and a pull request to `microsoft/CmdPal-Extensions` carries it.

How others get a trusted package onto a machine without the Store (read on 2026-11-20). Scoop
only moves files; Command Palette finds an extension only through the package identity of an
installed MSIX, so the MSIX must carry a signature the machine already trusts.

- **PowerToys** (scoop `extras/bucket/powertoys.json`, commit `30249ddf23`): scoop does not run
  the installer. It extracts the MSI from `PowerToysUserSetup-*.exe`. The extracted files
  include `WinUI3Apps/CmdPal/Microsoft.CmdPal.UI_<version>_x64.msix`, signed by Microsoft's own
  certificate: the installed `Microsoft.CommandPalette` reports `SignatureKind` `Developer` and
  the publisher `CN=Microsoft Corporation`. Who registers that MSIX was not checked; the scoop
  manifest does not.
- **ProcessKiller** ([8LWXpg/CmdPal-ProcessKiller](https://github.com/8LWXpg/CmdPal-ProcessKiller)):
  the plan of this item, run by hand. Its repository has no workflows. The script
  `scripts/publish-msstore-msix.ps1` asks `store.rg-adguard.net` for the bundle of the Store
  product ID, downloads it, uploads it to the latest tag with `gh release upload --clobber`, and
  runs `komac update` with the asset URL. The author ran it 6 days after the release v1.2.0,
  and 5 weeks after v1.1.1. The script checks neither the signer nor the version: it takes the
  last `.msixbundle` link in the response. Its own builds go out next to it, self-signed; they
  install only after `sudo winapp cert install cert.pfx`, so with admin rights.
- **Weather** ([baldbeardedbuilder/WeatherExtension](https://github.com/baldbeardedbuilder/WeatherExtension)):
  a certificate of its own. `release.yml` signs the MSIX with Azure Artifact Signing
  (`azure/artifact-signing-action`) under `CN=Bald Bearded Builder LLC`, a chain that ends at a
  public root, so Windows trusts it without an import (`SignatureKind` `Developer`). WinGet gets
  that MSIX through `winget-releaser`. A separate job builds a second MSIX with the Store
  publisher for the Store. The two packages have different identities, so they are two apps
  on one machine.

Raised on 2026-11-19.

**Scope Decisions**:
- **A script run by hand, not a scheduled workflow** (the author, 2026-11-20): replaces the
  second workflow decided on 2026-11-19. ProcessKiller has run this way since its first
  Store-signed release, and the script is proven on the author's machine. A GitHub runner may
  not get an answer from `store.rg-adguard.net`, and `winget download --source msstore` needs
  an Entra ID sign-in with admin roles. The cost is a manual step per release, days after it.
  The check of signer and version stays, so a wrong file still never reaches the release.
- **GitHub hosts the bundle, not a Store link** (2026-11-19): scoop needs a stable URL and a
  hash, and a winget-pkgs manifest needs a public installer URL. The Store gives out no stable,
  documented download link, and managed machines may not reach its servers.
- **The Store's signature, not a certificate of our own** (the author, 2026-11-20): Azure
  Artifact Signing, as Weather uses it, would sign at release time with no wait for
  certification. It costs a paid Azure subscription and an identity check, and it gives a
  second package identity next to the Store's. The Store-signed bundle costs nothing and keeps
  one identity everywhere. ProcessKiller shows that it works, by hand.

**Acceptance Criteria**:
- [ ] Each GitHub release has the Store-signed `.msixbundle` of its version as an asset
- [ ] `scripts/publish-store-bundle.ps1` attaches the Store-signed bundle to the latest release and runs `komac update`, and stops without an upload when the signer is not the Store's certificate or the version differs
- [ ] `microsoft/winget-pkgs` has a manifest for the extension with that asset as its installer, and a new release updates it
- [ ] `store/gallery/extension.json` lists a `winget` install source next to `msstore`, and the Gallery shows both
- [ ] On a machine without the Store and with the winget command line turned off, the Gallery's WinGet button installs the extension, and `Get-AppxPackage` shows `SignatureKind` `Store`
- [ ] A scoop manifest installs the bundle with `Add-AppxPackage` and removes it with `Remove-AppxPackage`, without admin rights or Developer Mode
- [ ] The README says how to install the extension through WinGet and scoop

**Open Questions**:

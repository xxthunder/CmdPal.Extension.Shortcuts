# [CPS-021] The build script's tests fail on Windows when they run under build.cs check

**Status**: Open
**Priority**: High
**Component**: `tests/FoldersCatalog.Tests/BuildScriptTests.cs`, `tests/FoldersCatalog.Tests/ToolRunner.cs`, `build.cs`

**Summary**:
As the author, I want `dotnet run build.cs -- check` to pass on my Windows machine, so that the local check before a UAT says the same as CI.

**Description**:
`BuildScriptTests` starts `dotnet run build.cs -- ...` for each test (`ToolRunner.RunFile`). A file-based app is built once into a cache folder named after its path, `%TEMP%\dotnet\runfile\build-<hash>\bin\debug\build.exe`. Under `dotnet run build.cs -- check`, the outer `build.exe` is still running while the library tests run. When a test's `dotnet run build.cs` rebuilds, it tries to overwrite that `build.exe`. Windows refuses: `Access to the path '...\build.exe' is denied.` Linux allows replacing a running executable, so the gate in the container does not see it.

Evidence from the author's Windows machine (2026-11-22, .NET SDK 10.0.404, the only SDK installed):
- `dotnet test tests/FoldersCatalog.Tests/FoldersCatalog.Tests.csproj --filter BuildScriptTests` passes 8 of 8, with no outer `build.exe` running.
- `dotnet run build.cs -- check` on `develop` fails all 8 `BuildScriptTests`.
  - Six fail with the access-denied message above.
  - `NoTarget_PrintsUsageAndExits2` and `UnknownTarget_PrintsUsageAndExits2` get exit code 1 instead of 2. The failed rebuild makes `dotnet run` exit 1 before the script runs.
- The other 130 tests pass.

The failure dates from CPS-013, when the library tests moved behind `build.cs check`.

Open question: the Windows CI job runs the same `dotnet run build.cs -- check` and passes. There the inner run apparently finds the build up to date and does not rebuild. Why the up-to-date check differs on the author's machine is not known. The fix must not depend on it.

Directions to weigh:
- The tests run a copy of `build.cs` from a temporary folder, which gives it a cache folder of its own. The script takes its root from its own folder, so the expected paths of the bundle test change.
- The tests' `dotnet run` builds into a separate output folder, if file-based apps support that. Check the current .NET 10 documentation first.
- `build.cs` itself avoids the case where it is already running.

**Acceptance Criteria**:
- [ ] `dotnet run build.cs -- check` passes on Windows with the build script's cache already built, as on the author's machine
- [ ] `BuildScriptTests` still passes when run alone, on Windows and in the gate's Linux container
- [ ] The cause of the rebuild, or why the fix makes it irrelevant, is stated in the item
- [ ] All existing tests continue to pass
